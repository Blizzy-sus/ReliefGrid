# ReliefGrid: disaster relief resource allocation

ReliefGrid coordinates **relief camps, warehouses, administrators and volunteers** during floods, cyclones and other emergencies. Its core is a *priority-based, explainable allocation engine* that shares scarce supplies fairly when demand exceeds stock, backed by a relational database designed so that **stock can never be over-allocated** and every decision leaves an auditable trail.

> All places, organisations and people in the demo data are fictional.

| | |
|---|---|
| **Stack** | Node.js 22 · Express 5 · SQLite (built-in `node:sqlite`) · vanilla ES-module front end (no build step) |
| **Only runtime dependency** | `express` |
| **Database** | 23 tables, 9 views, 21 triggers, 24 indexes, 4 versioned SQL migrations |
| **Tests** | 71 automated tests (`npm test`), plus a scenario harness (`npm run scenarios`) |

## Quick start

Requirements: **Node.js 22.13 or newer** (no database server to install: SQLite ships inside Node).

```bash
npm install
npm run seed      # creates data/reliefgrid.db with the demo incident (replaces any existing file)
npm start         # http://localhost:3000
```

On Windows you can instead **double-click `start-reliefgrid.bat`**: it installs dependencies and loads the demo data on first run, starts the server and opens the browser.

Then open <http://localhost:3000>. The sign-in page offers one-click demo accounts. Every demo account uses the password `ReliefGrid@2026`.

| Account | Role | Scope |
|---|---|---|
| `admin` | Administrator | whole network; the only role that runs allocation |
| `wm_thanjavur`, `wm_nagapattinam`, `wm_tiruvarur`, `wm_chidambaram` | Warehouse manager | own warehouse |
| `coord_thalaignayar`, `coord_nagoor`, `coord_marudhur`, … (one per camp) | Camp coordinator | own camp |
| `vol_asha`, `vol_ravi`, `vol_meena`, `vol_karthik`, `vol_fatima` | Volunteer | assigned shipments |

Other commands:

| Command | What it does |
|---|---|
| `npm test` | runs all 71 tests (about 5 s) |
| `npm run scenarios` | runs the allocation scenarios and regenerates [docs/RESULTS.md](docs/RESULTS.md) |
| `npm run migrate` | applies any pending migrations to the database file without touching data |
| `npm run dev` | starts the server with file watching |
| `node --disable-warning=ExperimentalWarning scripts/run-queries.js` | prints the results of the 17 showcase SQL queries in [db/queries.sql](db/queries.sql) |

Environment variables: `PORT` (default 3000), `RELIEFGRID_DB` (database file, default `data/reliefgrid.db`), `NODE_ENV=production` (disables the demo-account shortcuts on the sign-in page).

> `node:sqlite` is flagged "experimental" in Node 22 and prints a warning; the npm scripts silence it with `--disable-warning=ExperimentalWarning`.

## A five-minute walkthrough

1. **Dashboard** (`admin`): situation map, alerts, supply versus demand. Several items are short: water, ORS, insulin, tarpaulins.
2. **Allocation → Preview allocation.** Open an item (e.g. *Packaged drinking water*): each request line shows its priority score broken into urgency × vulnerability × waiting time, how much it would receive, and a plain-language explanation. Critical camps end up around 90% covered, Low-urgency ones around 15%, nobody at zero.
3. **Commit allocation.** One transaction reserves the stock, writes the immutable decision record and plans shipments. Open the new run in *Allocation history*.
4. Sign out and in as **`wm_thanjavur`** → *Shipments* → **Dispatch** one (stock leaves the warehouse; the ledger records it).
5. As **`vol_asha`**: claim the in-transit shipment and **Confirm delivery**, entering a smaller received quantity for one line. The shortfall returns to the request automatically.
6. As **`coord_thalaignayar`**: raise a **New request** (try asking for 40,000 L of water: the planning standard trims it and says why), then record a **Distribution**.
7. Back as `admin`: **Administration → Data integrity** (all reconciliation checks pass), **Audit trail**, and **Analytics**.

## Features

- **Camps, warehouses, items and inventory** with reorder levels and an append-only stock ledger.
- **Requests** with four urgency levels, quantities checked against a per-person planning standard.
- **Priority-based allocation** that is deterministic, fair across successive rounds, and explained line by line ([docs/ALLOCATION.md](docs/ALLOCATION.md)).
- **Shipments** generated by the allocation: plan → dispatch → in transit → delivered/cancelled, with partial-delivery handling and an automatic timeline.
- **Distribution records** closing the loop at the camp.
- **Dashboards and analytics:** map, shortage/SLA/low-stock/delay alerts, coverage and time-to-delivery by urgency.
- **Authentication and role-based access**, enforced in the API *and* by database constraints.
- **Audit trail and self-checks:** every action is logged; reconciliation views prove the ledgers add up.

## Known limitations

- **SQLite is a single-writer database.** That is a good fit for one control room (and gives simple, strong isolation) but not for many concurrent write-heavy nodes; the schema and SQL are portable to PostgreSQL, though the triggers would need rewriting in PL/pgSQL.
- **Sourcing is greedy** (highest priority first, nearest warehouse first), not a global minimum-distance optimum.
- **The map is schematic** (no tiles, works offline); distances are straight-line × a detour factor, not road routing.
- No e-mail/SMS notifications, no file attachments, no HTTPS (put it behind a reverse proxy), login throttling is per process.
- The UI has been exercised manually in a browser, not with automated browser tests (see [docs/TESTING.md](docs/TESTING.md)).
